\chapter{Methodology}
\label{chap:Three}

This chapter describes the concrete methods used to design, implement, and evaluate the "Truth Scanner" — a neuro-symbolic pipeline that translates informal textbook mathematics into machine-checked Lean~4 code. The work proceeded in clearly-defined phases: environment setup and learning, selection and taxonomy of source material, manual formalization to build a gold standard, construction of an automated translator and repair loop, and empirical evaluation.

\section{Overview of the Neuro-Symbolic Pipeline}
\label{sec:pipeline-overview}

The pipeline unifies two components:

\begin{itemize}
    \item \textbf{Neuro component (LLM)}: generates candidate formal code from informal English, guided by carefully constructed prompts that enforce typing and syntax.
    \item \textbf{Symbolic component (Lean~4)}: deterministically verifies, rejects, and reports errors for generated code; the compiler output is used as feedback for iterative repair.
\end{itemize}

Figure~\ref{fig:pipeline_arch} (in the main document) illustrates the high-level flow: English input $\to$ LLM translation $\to$ Lean~4 verifier $\to$ verified formal object.

\section{Phase 1: Learning and Environment Setup}
\label{sec:phase1-learning}

The project first established a stable, reproducible toolchain:

\begin{itemize}
    \item \textbf{Lean~4}: installed the stable Lean~4 toolchain and configured the local lake/lean-toolchain used in the repository.
    \item \textbf{Mathlib and Libraries}: configured access to community libraries where appropriate and prepared a minimal collection of helper modules used in the manual baseline definitions.
    \item \textbf{Editor Integration}: used the Lean VS~Code extension during manual formalization to inspect goals and proof states interactively.
\end{itemize}

Hands-on practice (the Natural Number Game and small lemma exercises) ensured fluency with tactics and dependent-type style used throughout the rest of the work.

\section{Phase 2: Source Selection and Taxonomy}
\label{sec:phase2-selection}

Selected source material came from a standard undergraduate textbook (Rosen's \textit{Discrete Mathematics}). Selection criteria targeted definitions and theorems that are:

\begin{itemize}
    \item Representative of typical informal mathematical exposition, and
    \item Small-to-moderate in proof complexity (suitable for iteration during repair-loop development).
\end{itemize}

For each chosen item we created a taxonomy mapping the English description to a proposed Lean type signature, a list of required lemmas from Mathlib, and explicit notes about implicit assumptions (e.g. domain restrictions, non-empty hypotheses, or implicit coercions).

\section{Phase 3: Manual Formalization (Gold Standard)}
\label{sec:phase3-manual}

Before automation, a manual formalization baseline was produced. The purpose of this baseline was threefold:

\begin{enumerate}
    \item Provide ground-truth Lean~4 files against which automated outputs are compared.
    \item Expose common translation patterns and the idiomatic Lean encodings for textbook phrases.
    \item Seed prompt examples and few-shot contexts for LLM prompt engineering.
\end{enumerate}

Deliverables from this phase include a set of verified \texttt{*.lean} files (in the \texttt{Lean/} folder) and an analysis document enumerating common ambiguities encountered while mapping informal prose to dependent-type signatures.

\section{Phase 4: Automated Translation and Prompt Engineering}
\label{sec:phase4-pipeline}

The automated translator is implemented in \texttt{scripts/llm\_translator.py}. Key engineering choices that improved first-pass compilation rates were:

\begin{itemize}
    \item \textbf{Strict system-level instructions}: enforce raw Lean syntax (no Markdown), explicit variable typing, and no conversational filler.
    \item \textbf{Sanitization filter}: strip Markdown fences, trailing commentary, and non-code prefixes before saving a candidate to disk.
    \item \textbf{Typed templates}: provide the LLM with expected type signatures (e.g., ``forall (x : $\alpha$)'' rather than ``forall x'') to reduce universe and inference errors.
\end{itemize}

The script supports a \texttt{--report} mode to generate Phase~III analysis artifacts and plots (see \texttt{Phase3\_Analysis\_Report.md} and images in \texttt{img/}).

\section{Phase 5: Iterative Repair Loop ($\Phi$ mapping)}
\label{sec:phase5-repair}

Automation is completed by an iterative repair loop that transforms compiler errors into focused correction prompts. Formally, the repair mapping is implemented as:
\[ \Phi : E \times S \to P, \]
where $S$ is the current Lean source, $E$ is the Lean~4 compiler error trace, and $P$ is the correction prompt sent to the LLM.

Practical implementation details:

\begin{itemize}
    \item \textbf{Error tokenization and truncation}: compiler traces are truncated to a short window (configurable \texttt{E\_trunc}) to avoid overloading the model with irrelevant verbosity.
    \item \textbf{Max retries and graceful fallback}: the loop uses a conservative \texttt{max\_retries=5}. If the loop cannot reach a verified state, the case is flagged and routed to the Manual Auto-Formalization Benchmark for human inspection.
    \item \textbf{State sanitization}: before each compile cycle the candidate source is validated by a sanitization step that removes non-Lean characters and ensures the file is saved in UTF-8.
\end{itemize}

These safeguards proved essential in practice to avoid oscillatory or divergent behavior during automated repair.

\section{Phase 6: Evaluation and Current Status}
\label{sec:phase6-eval}

The evaluation phase measured translation success rates, repair-loop efficiency, and categorized failure modes. Key outcomes achieved and reflected across the repository are:

\begin{itemize}
    \item \textbf{Working translator pipeline}: \texttt{scripts/llm\_translator.py} is usable to generate candidate \texttt{.lean} files from textbook text and to iterate repairs against Lean~4.
    \item \textbf{Empirical analysis}: Phase~III reports and plots (in \texttt{Phase3\_Analysis\_Report.md} and \texttt{img/}) summarize success/failure rates and dominant error modes (type inference failures, universe mismatches, and Markdown hallucinations).
    \item \textbf{Repository deliverables}: verified \texttt{*.lean} files, the translator script, analysis reports, and the final compiled \texttt{main.pdf} are present in the workspace.
\end{itemize}

\section{Reproducibility and Running the Pipeline}
\label{sec:repro}

To reproduce the automated translation and repair experiments locally:

\begin{enumerate}
    \item Ensure the Lean toolchain and Python virtual environment are active (see repository README).
    \item Run the translator on a short example: \texttt{python scripts/llm\_translator.py --text "<English definition>" --output Output\_1.lean}.
    \item Use \texttt{--report} to regenerate the Phase~III analysis artifacts.
\end{enumerate}

\section{Summary}

The methodology evolved from manual formalization to a working automated pipeline with a defensible repair strategy. The practical lessons — strict typing in prompts, robust sanitization, truncated error contexts, and a conservative retry policy — are central contributions enabling the rest of this thesis' empirical findings.
